# Rubric: is this plan ready to post and build from?

Grade only from the evidence named in each row. Judge the plan against
the issue and the repro evidence in the package, never the write-up's
headings or length. A short plan can be ready. A long, confident plan
can still be a hold.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| cause_grounded | The plan's stated cause, read against the repro evidence block (its controls, timings, and artifacts). A theory in the thread highlights is not evidence for the cause. | Pass if the plan states a mechanism and that mechanism fits what the repro evidence shows: the controls and artifacts do not rule it out, and the plan does not blame a subsystem the evidence has already excluded. Fail if the plan states no mechanism, or the mechanism contradicts the repro (the cost remains with that subsystem out of the loop, a control run of the blamed component succeeds, or the artifact appears before the blamed step runs). A cause copied from a thread comment still fails when this package's repro evidence contradicts it. | required |
| scope_bounded | The plan's in-scope work and its not-in-scope or deferred work, read against the issue's reported symptom. | Pass if the work the plan commits to is one change for that symptom, and the plan says what it will change and what it will not. Checking the same bug at sibling sites in the same function, then explicitly not fixing anything further, still passes. Deferring a larger rework and saying so passes. Fail if the plan commits to extra projects the issue did not ask for (a migration, a new subsystem, a rewrite of a neighboring feature, a settings UI, a CI matrix for a new architecture, or a list of while-in-the-area fixes), even when the first item is the right fix. | required |
| can_start | The plan's named files or code areas, plus the approach steps that say what will be edited there. | Pass if a stranger could open a named file or code area and start the described edit. An unknown about the exact line inside that named area still passes when the edit itself is described. Fail if no file or area is named, or the steps only investigate, profile, or "fix it once the cause is clear," with the edit itself undecided ("somewhere," "upstream or vendored, whichever is easier"). | required |
| test_decisive | The plan's test plan, read against the repro evidence's steps and the issue's expected behavior. | Pass if the test plan names what will be run (the repro steps, a named command, or a test that encodes them) and a concrete result for this bug (an exit code, a specific printed value, a color, a timing, a count, or an assertion about the symptom). Fail if success is a feeling ("feel fast," "feel broken," "look much better") or the only check is "run the full suite and make sure nothing regresses" with no result stated for the reported behavior. | required |
| thread_followed | Thread highlights whose role is OWNER, COLLABORATOR, or MEMBER and that name a file, a patch to test, an approach to use, or an approach to avoid, read against the plan and the plan comment. Comments whose role is NONE are not directions. | Pass if the thread has no such direction, or the plan or the plan comment follows it, or names it and explains a narrower alternative. Fail if such a direction is present and both the plan and the plan comment proceed as if it were not there (for example a docs-only workaround while an owner isolated a source file and asked for a patched binary to be tested). | required |
| ai_disclosure | The repo-facts contribution-policy line, plus the plan comment. | Fail only when that policy requires disclosing AI use on issues or comments (wording such as "must be disclosed" or "AI-assisted issues and comments must" disclose) AND the plan comment does not disclose the tool or that AI assistance was used. Pass when the policy is silent, when it only sets conditions for pull requests, when it only requires human-written comments or that the author understand the code, or when the plan comment discloses. | required |
| unknowns_honest | The plan's risks, unknowns, or deviation notes, if any. | Pass if the plan labels a real unknown as unknown, or simply does not claim an unmeasured result as fact. Fail if the plan states a guess about an unmeasured cause or cost as if it were already shown. Never changes the verdict. | preferred |

## Verdict rule

Accept only if every required check (`cause_grounded`, `scope_bounded`, `can_start`, `test_decisive`, `thread_followed`, `ai_disclosure`) is `pass`. A `fail` or `unclear` on any required check is a reject. The preferred check `unknowns_honest` never changes the verdict, whether it is `pass`, `fail`, or `unclear`. `unclear` means the evidence named for that check is absent from the package, and on a required check it counts as fail.
